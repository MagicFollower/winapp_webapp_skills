## 关闭时明显卡顿且没有退场动画

**出现：2026-10-27 22:56（实测复现：修复前包 `WINDOW_GONE_MS=452 / 543`，全程冻结；用户反馈在此之前）**
**修复：2026-10-27 23:02（v0.2.0 build 230213 / 230225 发布包）**

### 问题

点关闭后窗口僵住约半秒才消失，且没有任何动画；运行中有事件积压时更久。

### 成因

`MainWindow_Closing` 在 UI 线程同步调 `Vm.Shutdown()`，里面连着做三件慢事：`IndexWatcher.Dispose()`（排空事件队列并等索引锁）、`FileIndex.Save()`（Compact + 写 65 MB 快照 + `.bak` 复制）；WPF 侧也没有退场动画，窗口是瞬间被销毁的。

### 核心修复方案

关闭拆成两段。`BeginShutdown()` 只跑 UI 线程且必须快（停定时器、取消后台任务、摘走 watcher）；`FinishShutdownAsync()` 在后台排空 watcher 并写快照。`Closing` 首次进入一律 `e.Cancel=true`，先显示「正在保存索引…」遮罩，再对根 `Grid` 做 170 ms 淡出 + 0.975 缩放，动画结束才真正 `Close()`；`Closed` 里最多再等 1.2 s，等不到就 `Environment.Exit(0)`。快照是「写 .tmp → Move」的原子替换，中途被杀只会丢这一次保存，不会留下半份索引。顺带把 `StopWatcher()` 改成只摘不 Dispose，F5 重建与关闭实时开关同样不再卡 UI。

### 改动点

`app/MainWindow.xaml`（`RootGrid`/`RootScale`/`ClosingOverlay`）、`app/MainWindow.xaml.cs`（两段式关闭 + 动画 + 宽限退出）、`app/ViewModels/MainViewModel.cs`（`BeginShutdown`/`FinishShutdownAsync`/`StopWatcher` 语义）。`lib/` 未改。

### 验证

同一「运行中创建 3000 文件后立刻关闭」场景：窗口从屏幕消失由 **452–543 ms（全程冻结）** 降到 **236–250 ms（带淡出）**；进程退出 664–1092 ms，此时窗口已不可见。无脏数据时关闭 231–317 ms。selftest 0（含主窗口 XAML 解析）。

## 一条 Renamed 事件删掉整棵 C 盘索引（数据丢失）

**出现：2026-10-27 22:53:06.223（`%LOCALAPPDATA%\IndexApp\index-diagnostics.log` 记录的 root-removal 时间戳）**
**修复验证：2026-10-27 22:57–22:58（三轮洪水/对账循环）｜发布：23:02**

### 问题

默认全盘快照从 774,220 条掉到 236,027 条；`C:\Windows`、`C:\Program Files` 等整棵消失，只剩 `C:\Users`；解析快照发现 **7,273 个重复的 `C:\` 根条目**。

### 成因

`FileSystemWatcher` 偶尔报出旧名字为空的 `Renamed` 事件，`OldFullPath` 退化成卷根 `C:\`。`RenamePathLocked` 把它解析到索引根条目（`ParentIndex < 0`），随后按「目标类型不符」走 `RemoveSubtreeLocked(index)`，等于连根拔掉整棵卷树；之后每次解析 `C:\xxx` 的父目录都失败，`EnsureDirectoryLocked` 又按 `name = full` 兜底新建一个 `C:\` 根，于是复制出上千个根。

### 核心修复方案

三层护栏，全部落在引擎而不是只堵 watcher：

1. 根条目不参与重命名/删除/类型翻转——`RenamePathLocked`、`RemovePathLocked`、`UpsertPathLocked` 命中 `ParentIndex < 0` 一律返回 0，索引根只能被重建换掉。
2. `RenamePathLocked` 先校验新路径是具体条目（有文件名、有父目录）再动 `existingNew`，避免畸形目标先删子树。
3. `EnsureDirectoryLocked` 不再凭空造根：路径没有文件名就返回 -1。

取证方式：在 `RemoveSubtreeLocked` 里对根条目删除写一条带 `Environment.StackTrace` 的日志，实测栈为 `IndexWatcher.Drain → FileIndex.ApplyChanges → RenamePathLocked → RemoveSubtreeLocked(path=C:\)`。

### 改动点

`src/IndexCore/FileIndex.cs`（四处护栏 + `LogRootRemoval` 与 `rootRemovals` 诊断计数）、`tests/IndexCore.Tests/Program.cs`（洪水与根事件回归）。`lib/` 未改。

### 验证

引擎测试 70 → **83 PASS**，新增「root-sourced rename/delete 被忽略且条目数不变」等回归；真实场景连跑三轮「洪水创建 3000 文件 → 关闭 → 重启对账 3000 删除 → 再洪水」，快照稳定在 65.9–66.1 MB，诊断日志无根删除记录。坏快照已删除并全量重建。

## M2.0 实时增量：目录监视 + 启动后台对账

**出现：2026-10-27 11:34（工作区时间戳，用户提出「迭代 M2 版本」）**
**实测：12:18–13:26（验收进程启动时间戳）｜收尾与发布：19:24–20:07**

### 问题

M1 运行中新增/删除/重命名文件不会刷新；应用关闭期间的变化也要 F5 全量重建。本机非管理员，USN/MFT/服务无法验证。

### 成因

`FileIndex` 构建后只读、没有事件源；直接上 USN/MFT 会被权限挡住，且无法交付可复现验收。

### 核心修复方案

1. `FileIndex` 改为追加式条目 + 墓碑 + 父子链，支持 `ApplyChanges` / `Reconcile` / `Compact`；快照仍是 `IDX1` version 1，写盘前压实活条目，M1 与 M2 快照互读。
2. 新增 `IndexWatcher`：`FileSystemWatcher` 事件 500 ms 合并，排除目录入队前过滤，缓冲区溢出置 `Overflowed` 并提示 F5。
3. 启动先出旧快照结果，再挂 watcher，随后后台分块 `Reconcile`（只 stat 目录 mtime，变化目录才枚举），完成后 `Compact` + Aggressive GC。
4. UI 增加 `LiveStatusText` 与 ASCII `IndexStateCode`（ready/reconciling/live/off/overflow/failed），设置面板加 `liveRefresh` 开关。
5. 默认索引根排除 `%LOCALAPPDATA%\IndexApp`、`%APPDATA%\IndexApp` 与快照文件，避免自己监视自己。
6. 内存治理：数组/arena 改 25% 增长、对账路径不写缓存、目录解析只留 5000 条缓存、`System.GC.ConserveMemory=9`。

弃法与代价：弃了同步启动对账（全盘 11.5 万目录一次 stat 3–5 s，会把冷启动 3 s 闸门打爆）；弃了整张目录路径字典常驻（把私有内存推到 400 MB+）。

### 改动点

`src/IndexCore/FileIndex.cs`、`src/IndexCore/IndexWatcher.cs`、`src/IndexCore/Models.cs`、`src/IndexCore/NameArena.cs`、`app/ViewModels/MainViewModel.cs`、`app/MainWindow.xaml`、`app/MainWindow.xaml.cs`、`app/Views/SettingsOverlay.xaml`、`app/Services/SettingsService.cs`、`app/Services/SelfTest.cs`、`tests/IndexCore.Tests/Program.cs`、`bench/IndexCore.Bench/Program.cs`、`app/IndexApp.csproj`（版本 0.2.0 + GC 配置）。`lib/` 未改。

### 验证

- 引擎 83 PASS、StartUI4 70 PASS + 1 INFO、退出码 0。
- 实时新增/删除：独立测试根运行中创建/删除文件，不按 F5，1.5 s 内结果与状态同步。
- 离线对账：关闭后新增/删除/重命名，重启显示「启动对账 新增 2 / 删除 2 / 更新 0」并搜索一致。
- 性能：关键词 UI 97–127 ms；`--perf` 856 帧 max 42.3 ms、over100=0（19:24:36 数据）。
- 内存：框架依赖包 240.3–265.9 MB 达标；自包含包 316.5–371.6 MB 超标，如实记录未写成通过。
- 空查询 201–359 ms 超过 200 ms 闸门，如实记录。

**完成：2026-10-27 07:56（文档落盘时间戳）**

### 问题与结论

USN 是 NTFS 更新序列号日志：卷上维护一个环形 `$UsnJrnl:$J`，按 `JournalID + Usn` 记录每次元数据变更。增量索引即「快照里存 checkpoint，启动后从 checkpoint 回放到当前」，日志回绕或 `JournalID` 变化时退回全量重建。文档同时记清 M1 当时没有 USN、以及读取需要管理员权限。

新增 `docs/USN增量-原理与生效流程.md`（定义、记录结构、事件映射、9 步生效流程、验收判据、Q&A）。2026-10-27 20:07 因 M2.0 交付同步更正「当前不会实时刷新」的旧结论。
